# Production gap analysis

Status is based on executed/reviewed repository evidence as of 2026-09-10.
Absent evidence is not treated as a passing requirement.

| Severity | Gap | Why it blocks or constrains release | Required closure evidence |
| --- | --- | --- | --- |
| CRITICAL | No storage/WAL correctness defect is known open. Three were found and fixed after this audit opened (the WAL fsync latch, the poisoned-create path, and the missing-segment fail-open — rows below); their absence beforehand reflected the reach of the tests then available, not the engine's state | An absence of discovered defects is not a pass, and all three show I/O-failure and recovery paths were the blind spot | Retain continuous crash/corruption gate evidence. Fault injection now reaches past the WAL barrier — page write/read, data fsync, directory fsync, nonce reservation, undo barrier, backup and restore — via `tests/fault`, and `tests/upgrade` replays shipped-binary fixtures; keep extending both as new durable paths land |
| HIGH | P28 installer exit gate remains open; Windows/macOS execution is host-blocked | The repository's current release gate is unmet | Complete or explicitly de-scope with release authority. M2 is now closed: `internal/crypto` supports a second independent unlock key sealing the same KEK (keystore `NSKS` v2, written only on opt-in), exposed as `nextsql key status / add-recovery / verify-recovery / remove-recovery / recover` for both keystores, and `nextsql setup --recovery-key-out` plus the Setup wizard export and verify one for each keystore during a first install, holding Finish until the operator confirms they saved both. Verified live end to end: a wizard-shaped install, both root key files deleted, both keystores recovered, pre-loss rows intact and new writes accepted. What remains is Windows/macOS execution, which still needs those hosts |
| MEDIUM (was HIGH) | No full production release command previously combined storage, WAL/recovery, protocol, auth and backup evidence | Individual tests can hide an unrun required category | CI is now wired: `.github/workflows/production-gate.yml` runs `make test-production` on `master`/version tags and retains its complete log for 30 days. **The profile itself was incomplete until log #256**: it ran 24 packages and none of `internal/executor`, `internal/sql/...`, `internal/replication`, `tests/crash`, `tests/ha` or `tests/integration`, so a wrong query answer, a failed failover or a broken driver could not fail it — the six aggregate defects of logs #250-#254 would all have passed. It now runs 36 packages including a `-race` pass over the executor. A **local** green run is retained at `docs/production/evidence/2026-09-09-test-production.md` (exit 0, 36 packages, no failure, panic, data race or timeout). That is not a substitute: the first green **hosted**-run artifact remains the required evidence; see `AFTER.md`. |
| MEDIUM (was HIGH) | The durable test profile must not run on a RAM-backed filesystem | `/tmp` is `tmpfs` on at least one development host, so an unconfigured run fsyncs into RAM and proves nothing about durability | CI sets `NEXTSQL_REQUIRE_DURABLE_FS=1` and retains the `test scratch: … (filesystem: …)` line for 30 days. The retained local run above was made with that variable set and records `filesystem: ext2/ext3` — so the refusal path is exercised and the volume is a real block device on this host. The first retained **hosted**-run artifact still needs review; an absent artifact is not a pass. |
| CLOSED (was HIGH) | Limit model was fragmented; frame, SQL and descriptor limits were coupled and many operational limits were constants | Legitimate load and adversarial input could not be independently controlled | Closed: `internal/limits` is the single sorted catalog of operational defaults, absolute ceilings, units, zero semantics and rationale. It separates wire/frame/SQL/parameters/prepared state/results; memory; concurrency; time; and storage controls. `config.Load`, programmatic `Config.Validate`, `Marshal`/`WithSetting`, and `nextsqld` all use it; catalog, range, parser/validator, round-trip, protocol/server and race regressions cover it. `docs/limits.md` is generated and checked. Structural/format limits remain deliberately local to their encoding and are inventoried there. |
| CLOSED (was HIGH) | Disk-full, short-write, failed-fsync and EIO coverage is not demonstrated as a release profile | Durability claims require explicit I/O failure behavior | Closed: `tests/fault` is a named profile (`make test-fault`; also run by `test-pr`, `test-production`, `test-chaos`, `test-nightly`). The seam covers reads, positional and sequential writes, `fsync`/`fdatasync` and directory fsync, identifies the file and offset so one device can fail while another works, and reproduces genuine torn writes (`diskio.ShortWrite`). Eleven engine-level cases: checkpoint under a failing page write and under a failing data fsync, an unreadable page, a torn WAL write, `ENOSPC` that clears, a failed create, a failed nonce reservation (no AES-GCM nonce reuse), an unreadable log during redo, a failed undo barrier, and backup/restore on a full device. Each asserts its fault actually fired |
| CLOSED (was HIGH) | A failed WAL `fsync` did not latch, so the next flush declared the un-synced region durable and acknowledged a commit that a crash would lose | Acknowledged-commit loss after a transient device error — a durability violation | Closed: `internal/wal` latches a failed durability barrier; regression tests at the WAL boundary (`TestFailedSyncLatchesAndRefusesLaterCommits`) and end to end (`storage.TestCommitFailsClosedAfterDurabilityFault`), both verified to fail without the fix |
| CLOSED (was undetected) | `wal.Open` accepted a WAL whose segments no longer covered the redo boundary, so a database came up silently missing every acknowledged commit after that boundary and reported `status ok` | The next checkpoint installed over the gap, making the loss permanent; found by deleting the WAL segment from a retained fixture as a negative control | Closed: `wal.Open` fails closed with a `corruption` error naming `durable_lsn` and `redo_lsn` when no segment exists while anything was acknowledged, or when the oldest segment starts past the redo boundary. `wal.TestOpenRefusesMissingSegments` covers both, and a never-acknowledged empty log still opens; both failing cases were verified against the un-fixed code |
| CLOSED (was undetected) | A create that failed after the data file existed left the file behind, so every later create at that path returned `already_exists` | A full or failing device during `nextsql init` (or a hosted database create) permanently poisoned the path: the operator had to know to delete a file no usable database was ever built on | Closed: `file.Create` removes the file when its directory entry cannot be made durable, and `storage.open` unwinds exactly what a failed create made — the data file, the integrity sidecar, and only those WAL/undo directories that did not already exist. `tests/fault` covers the directory-fsync and undo-barrier variants; both were verified to fail without the fix |
| CLOSED (was undetected) | Aggregates over `system.*` tables failed with `unknown function`, and the two official-driver live suites that assert one were the only ones not run by any gate | A documented catalog query was broken, and the suites that would have caught it sat failing with no signal — a coverage hole, not only a SQL one | Closed: `internal/executor/system.go` answers scalar aggregates by driving `aggregate.Hash` with no grouping columns, so the accumulators are the user-table ones (`COUNT(*)` over an empty catalog is one row holding `0`; `LIMIT`/`OFFSET` bound the result, not the input; a bare column beside an aggregate is rejected as the binder rejects it). Eight regressions in `internal/executor/system_aggregate_test.go`, all verified to fail against the un-fixed evaluator. `tests/integration/drivers_test.go` now runs the Python and Ruby unit **and** live suites alongside Node/Bun/PHP, and each live gate fails if the suite skipped itself rather than connecting |
| CLOSED (was undetected) | `GROUP BY` on a computed or positional expression returned a wrong answer, and `HAVING COUNT(*)` could never match its selected aggregate (computed grouping is now implemented — log #253; positional grouping stays refused) | A silently wrong aggregate result is the worst failure class in the priority order — the query reported one collapsed group as though it were the grouped answer | Closed: the planner built group ordinals by dropping any item that was not a resolvable column, which collapsed the whole input into one implicit group rather than disabling grouping (`SELECT a + b, COUNT(*) ... GROUP BY a + b` answered a single bogus row). `GROUP BY` now requires a column reference, refused at bind time with the planner failing closed behind it; `binder.grouped` no longer treats two unidentifiable expressions as the same one. Separately, `HAVING` matched select items with `reflect.DeepEqual` against expressions already rebuilt with an empty **non-nil** `Args` slice, so a star aggregate never matched — both sides are now normalised identically. Six regressions in `internal/executor/group_by_correctness_test.go`, each verified to fail against the un-fixed code |
| CLOSED (was undetected) | Aggregates over a computed argument read as `COUNT(*)`, and an aggregate inside a larger expression answered an uninitialised empty cell (both are now implemented, not merely refused — logs #252 and #253) | Two more silently wrong aggregate results, found by using the log #250 defect as a search heuristic rather than by any test | Closed: an aggregate argument resolves to an input column ordinal whose "unresolved" value `-1` already meant *star*, so `COUNT(a + b)` counted every row and `MIN`/`MAX` over an expression returned `NULL`; and with no projection running after aggregation, `SELECT COUNT(*) + 1` fell through to a zero `types.Value`. Both are now refused at bind time. Window functions project after evaluation and are deliberately unaffected. Regressions in `internal/executor/group_by_correctness_test.go`, each verified against the un-fixed code. All 24 decoder fuzz targets, NULL/three-valued `WHERE`, `NOT IN` over a NULL-bearing subquery, outer-join cardinalities and `SUM` past `INT64` max were also checked and are correct |
| CLOSED (was HIGH) | Upgrade compatibility is not demonstrated against retained prior-release fixtures | A format change could strand production data | Closed: `tests/upgrade` (`make test-upgrade`; also run by `test-pr`, `test-production`, `test-nightly`) replays retained fixtures — real data directories written by the shipped `v0.0.1` binaries, clean and `SIGKILL`ed, with the query results and compatibility catalog that release printed. The current build must match every recorded result, keep the fixture principal's grants unchanged, write, restart, and backup/restore, and must leave every on-disk family inside the generating release's readable window (rollback preservation); with `NEXTSQL_UPGRADE_OLD_BINDIR` the released binaries themselves re-read the upgraded directory. Cut one pair per release with `scripts/make-upgrade-fixture.sh`. What remains is procedural: `RELEASING.md` now requires it |
| CLOSED (was MEDIUM) | Public error codes did not emit the stable `ERR_*` vocabulary on the wire | Client retry/diagnostics received only legacy lowercase internal classes | Closed by capability negotiation rather than a frame-version bump, which would have disconnected every existing client (`ReadFrame` accepts only version 1). `Hello.flags` bit `0x0002` requests the taxonomy; the server masks the request to what it implements, echoes it in an optional trailing `HelloOK` flags field, and appends the `ERR_*` name as an optional trailing error field. The legacy lowercase `code` is never replaced, so existing retry checks are untouched, and a client that requests nothing gets byte-identical v1 frames — asserted by a hand-rolled v1 client in `tests/integration`. All six official drivers request it and expose the name (`docs/error-codes.md` has the per-driver field table), verified live against a real server. `FuzzDecodeError`/`FuzzDecodeHelloOK` enforce canonical encoding; both found and fixed a real malleability where an empty trailing field decoded as an absent one. |
| CLOSED (was MEDIUM) | Documentation had a geometry-limit contradiction | Operators could make unsafe sizing decisions | Closed: fixed native `LINESTRING`/`POLYGON` stays at 256 vertices (`types.MaxGeoVertices`); general OGC `GEOMETRY`/`GEOGRAPHY` separately permits 65,536 total vertices, nesting depth 8 and 4,096 parts (`types.MaxSpatialVertices` / `MaxSpatialDepth` / `MaxSpatialParts`). The public limits, protocol/security reference tables and production report now distinguish the two; `docs/design-spatial.md` remains the detailed source-backed contract. |
| MEDIUM (partly closed) | Multi-day soak, constrained-memory profiles and benchmark comparison artifacts are not current release evidence | Predictability under sustained load is unproven without dated runs | A dated `constrained-memory-v1` run is now retained at `docs/production/evidence/2026-09-09-btree-soak-constrained.md` (10M operations over 8,192 pool pages under `GOMEMLIMIT=512MiB`/`GOGC=25`, `NEXTSQL_REQUIRE_DURABLE_FS=1`, ext4, PASS/exit 0, 34:01 wall, 132 MiB peak RSS). Producing it exposed two defects in the evidence plumbing itself, both fixed: every retained report recorded `elapsed_wall=mm` because the metrics extractor split GNU `time` output on `:` while the elapsed-time **label** contains colons — the headline number was never measured; and the artifact filename was the hardcoded literal `btree-100m-p16`, which described neither profile, so two different profiles produced names claiming the same shape. Still open: the normal 100M profile and the multi-day run — and the 100M profile is now **sized**, which it was not before. Started on this host it reaches 4M operations in 20 minutes and its own projection grows as the live set does: 3h04m at 1M ops (594K live), 5h58m at 2M (1.18M live), 7h34m at 3M (1.75M live), 7h56m at 4M (2.31M live), as throughput decays 31,369 → 3,360 ops/s. It needs a dedicated run of **8+ hours** on an idle machine, not a slot inside a working session; the attempt here was stopped and its partial artifacts discarded rather than retained as if complete. |
| CLOSED (was MEDIUM) | Raft election timings were hardcoded while the documentation presented them as defaults | `docs/ha.md` said "Default Raft timeouts: heartbeat / election 250 ms, lease 200 ms" and warned against lowering them, but `internal/replication` set them from constants and `Config` exposed no field, so an operator on a slower link or a contended node could not raise them. A cluster that cannot complete an election round inside its election timeout re-campaigns rather than converging — observed directly, twice, under gate load | Closed: `replication.Timings` carries all four intervals, `Config.Timings` accepts them, and `Open` resolves each unset one to its default and validates the set before starting Raft. `raft_heartbeat_ms` / `raft_election_ms` / `raft_leader_lease_ms` / `raft_commit_timeout_ms` are catalogued limits with flags and config keys. **The coupling that reverted the first attempt (log #256) is what the fix is built around**: the healthy-contact window is five of the *configured* heartbeat, not five of the default one, so `ReplicaHealth`, `FollowerReadHealthy` and the default `MAX STALENESS` of a `BOUNDED` read all widen with a raised heartbeat instead of judging every follower unhealthy between contacts — an executor gate names its own default window through `StalenessDefaulter`. The two protocol relationships (lease ≤ heartbeat ≤ election) are enforced at configuration time by `limits.CheckRaftTimings`, which `internal/config` and `internal/replication` share so the rule exists once; a sweep asserts every set `Resolve` accepts is one `raft.ValidateConfig` accepts. Coverage of its own, as the row required: live election, replication, **failover** and **partition** tests run on non-default intervals (`internal/replication/timing_cluster_test.go`), the freshness boundary is checked directly as a pure decision, and each assertion was verified to fail against the un-fixed code. `internal/limits` — which no gate ran — is now in the release profile |
| CLOSED (was LOW) | Test profile names were not standardized | Developer/CI invocation was less discoverable | Closed: named `make test-pr`, `test-production`, `test-fault`, `test-upgrade`, `test-nightly`, `test-chaos`, and `test-soak` targets are published and the production-gate workflow retains each CI evidence log for 30 days; `RELEASING.md` makes review of the release artifact mandatory. |
| CLOSED (was MEDIUM) | Every temporary test database preallocated the production ~256 MiB runway (`DefaultPreallocAheadPages`), because no suite chose one | A test that only checks backup listing and sorting built three databases plus three backups, so the profile wrote far more than it needed and a killed run stranded hundreds of MiB. The runway was also completely untested | Closed per suite, by measurement. `internal/backup` shrinks it in `TestMain` (201s → 3.3s on ext4). `internal/storage/btree` keeps the default: it does bulk inserts, which the runway exists for, and is worse without it (104s vs 115s). New `internal/storage/file` tests cover the runway at the production default, including that `fallocate` reserves real blocks rather than a sparse file |
| CLOSED (was LOW) | Undo-log `Flush` writes without an `fsync` of its own | Not a defect — undo state is re-derivable by redo and the WAL is the durability authority — but the asymmetry is undocumented and easy to misread during an audit | Closed: recorded in `docs/mvcc.md` ("UNDO durability"). The undo barriers that do exist (`Vacuum`, control file) were also moved onto the shared seam, so they are injectable and covered by `tests/fault` |
