The server fix is commit `1a2d8cfc92feb91662519a89200359d842febcf4`.
Its [hosted production gate](https://github.com/bzync/nextsql/actions/runs/40262530098)
passed, including the Admin UI job. The retained
[production profile log](2026-10-26-date-panic-production.log) records
`filesystem: ext2/ext3`, normal and race coverage for the executor, storage,
WAL, recovery, transactions and backup, plus fault, crash, HA, integration,
retained-fixture upgrade, authentication, protocol and CLI coverage. This
supersedes the incomplete local broad runs as evidence for the fix. The exact
versioned release commit must separately pass this gate before tagging.

## Local release artifacts

Go 1.26.10, linux/amd64; built with `scripts/build-linux-installer.sh --arch
amd64 --skip-rpm`. The .tar.gz, .run and .deb manifest checksums pass. Tarball
and Debian payloads contain identical binaries for nextsql, nextsqld,
nextsql-bench and nextsql-admin. Both the tarball and .run install successfully
into isolated workspace prefixes with separate XDG config/data directories and
no service or GUI launch. The .run also extracts and displays installer help.
The tarball CLI reports 0.0.6; an isolated daemon logs 0.0.6, rejects all four
malformed date-function probes (including the Launcher report), and answers a
valid DATE_ADD query afterward. These local build hashes are not substituted
for the eventual GitHub build's published asset digests.

Fixture generation preflight reproduced the existing helper's missing-database
startup failure. Adding explicit `--database default` to its initialization
command produces both clean and crash-recovery candidate archives. Those
preflight archives stay outside the retained fixture set; the release fixtures
will be generated only from the published release binaries. `bash -n` passes.

Docs lockfile installation/audit reports zero vulnerabilities. Docs lint,
release-catalog tests, TypeScript/production build (48 static routes), rendered
function-search verification, Go version compilation, and documentation parity
checks pass. The new curated release entry remains draft until actual GitHub
assets are published and synchronized.

## Bounded SLO measurement

Command, using the built release binary, with disk-backed TMPDIR:

```sh
GOMAXPROCS=4 nextsql-bench -slo -slo-max-rows 25000 \
  -slo-vectors 256 -slo-vector-queries 64 -json
```

The command exits 0 and validates its workload results. This is a bounded
measurement, not a full-scale performance sign-off. The
[raw report](2026-10-26-v0.0.6-slo.json) records CPU (Ryzen 5 7535HS), RAM
(14.3 GiB), ext4, 4096 buffer pages (64 MiB), concurrency 1, row widths,
queries, indexes, cache conditions, percentiles and throughput. AES-256-GCM,
WAL and fsync remain enabled. Authentication and authorization follow this
benchmark's existing embedded-session harness; this is not a network
authentication throughput measurement. Disk and memory counters emitted as
zero by individual report rows are not measured zero resource consumption.

Point/index, 25K bulk insert/update/delete, scan/aggregate/range/join, hybrid,
and the 256-vector HNSW rows meet their recorded targets. HNSW uses 8 dimensions
and 64 query samples: recall@10 1.000, p95 0.716 ms. This is not evidence for
the separate 1M-vector gate or a new general ANN claim.

Single-row insert and update **do not meet** the recorded latency targets on
this host: insert p50/p95/p99 2.482/48.797/59.240 ms, update
0.786/46.511/55.090 ms. The host also showed heavy I/O pressure during the
earlier local broad tests. No baseline comparison establishes the cause of
these tails; they are retained as preview limitations, not called a green
performance sign-off. No durability setting or target was reduced.
