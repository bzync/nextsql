# NextSQL 0.0.10 — HA and container first-start fixes

Upgrade if you run an HA cluster or the container image. `SHOW CLUSTER` now works on the nodes where operators need it, and first starts in containers fail less and finish sooner. This release changes no storage, WAL, catalog, or wire format.

## Fixed

- **`SHOW CLUSTER` answers on followers and with no leader.** It failed with `not the leader` or `no leader` under the default `STRONG` read consistency, although the operations runbooks use it on those nodes to confirm a new leader. `system.replication`, `system.raft`, and `system.replica_health` behave the same way.
- **A lost database now gets a clear error.** When a deployment has lost `nextsql.db`, `nextsql init`, `nextsql setup`, and the container's first start name the missing file instead of reporting `database is already initialized`. They still refuse to create a new database.
- **Changed settings no longer block a first start.** A container's first start replaces a `nextsql.conf` left by an earlier first start that did not finish, instead of failing with `config file ... already exists`.
- **HA first starts are faster.** Joining containers restore onto the data volume, which removes one full copy of the database per joining node. In three alternating runs on a desktop host, time to the first write went from 98 to 208 s on 0.0.9 to 43 to 90 s.

## Behavior changes

- These statements skip the read-consistency check only when they read one of those tables alone. A statement with a join, subquery, `UNION`, or `WITH` is checked as before, and other reads on a follower are still refused under `STRONG`.
- The rows are that node's own view, so a follower or a partitioned node can report a different state from the leader. `has_leader` shows whether the node currently sees a leader.
- A hand-edited `nextsql.conf` on a volume with no database is replaced at first start, and the container logs that it did so. Volumes that already have a database are not affected.

## Upgrade and compatibility

Stop the daemon, install the 0.0.10 Linux packages or pull the new image, and restart it. Confirm both the CLI and daemon report `0.0.10`.
There are no storage, WAL, catalog, or network protocol format breaks relative to 0.0.9.

Container users pin `docker.io/bzynchub/nextsql:0.0.10`. Image tags and release assets are immutable.

If you are upgrading from a release before 0.0.8, read the [0.0.8 release notes](0.0.8.md) first. That release fixed a rollback bug that could damage data, and upgrading does not repair existing damage. Run `nextsql check-pages` on a restored copy of a recent backup.

## Known issues

- An empty database occupies 386 MB because its data file and first WAL segment are preallocated, and a first HA start writes that six times. On a slow disk, this is most of the start time.
- If `NEXTSQL_DATABASE` also changed when `nextsql.db` was lost, the error is `existing registry does not match bootstrap database`, which does not name the missing file.
- If a joining HA container crashes while moving its restored files into place, it can fail to open until its data volume is cleared. The window is short, and this risk is not new.
