# NextSQL 0.0.8 — data-integrity fix for page reuse

Upgrade if you run any earlier release. A rollback could put pages still in use back on the page freelist, and a later write could then replace a live page with an empty one, with no error.

## What went wrong

Every rollback reloaded the page freelist from an older copy on disk. The idle task runtime aborts a transaction every 250 ms, so this needed no rollback from your application. It could happen during a migration or other write load once the freelist held pages, such as after a `DROP`.

There were two symptoms:

- Statements failed with `page already cached`, reported as `already_exists`.
- If the page had left the buffer pool, a live page was replaced with an empty one. A table could then become unreadable after acknowledged writes.

We reproduced this on the 0.0.7 code and did not test older releases. The reload dates back to the first commit, so treat every earlier release as affected.

## Check your database

Upgrading stops new damage but does not repair existing damage.

```bash
nextsql check-pages --data-dir DIR --key-file FILE
```

Stop `nextsqld` first, or run it on a restored copy of a recent backup. It exits 0 with `result clean`, or 5 with `result damaged`. It repairs nothing. On a cluster, check every node, because each has its own data file.

A clean result covers tree structure and page ownership. It does not prove that every row is present. A database that logged `page already cached` can still check clean, because that error usually aborts the statement before any damage commits.

If the result is `damaged`, stop writes. Then either restore the most recent backup that passes the check, or use `nextsql export` and `nextsql import` to move to a new data directory. See `docs/ops.md`.

## Behavior changes

- **`nextsqld` can refuse to start.** It stops if a live page is on the freelist, because its next writes could destroy that page. This check reads only internal pages, so it adds little startup time. It does not detect every kind of damage: a table with a broken leaf link still starts, and reads of that table fail with a corruption error.
- **`nextsql lifecycle upgrade` runs the full check** and fails on any page ownership damage.
- **The error code changed.** This failure now reports `corruption` instead of `already_exists`, and the message still contains `page already cached`. Remove any retry you added for it.

## Other fixes

- The idle task runtime no longer writes to the WAL on every poll.
- A rolled-back `CREATE TABLE` or `CREATE INDEX` no longer leaks the new tree's pages.
- A failed allocator reload no longer leaves a half-rebuilt freelist.
- A page allocation that fails because the buffer pool is exhausted no longer leaks the page id.

## Upgrade and compatibility

Stop the daemon, install the 0.0.8 Linux packages, and restart it. Confirm both the CLI and daemon report `0.0.8`.
There are no storage, WAL, catalog, or network protocol format breaks relative to 0.0.7.

Container users pin `docker.io/bzynchub/nextsql:0.0.8`. Image tags and release assets are immutable.

## Known issues

- `nextsql check-pages` runs offline only and has no repair mode.
- Pages left unreferenced by some rollbacks or failed commits are not reclaimed. This wastes space but is safe, and `check-pages` reports the count as `orphan_pages`.
