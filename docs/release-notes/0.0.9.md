# NextSQL 0.0.9 — container first-start fix

Upgrade if you run the container image. A fresh container could not start on earlier images, and `nextsql restore` and `verify` failed in the image under most non-default UIDs. This release has no engine changes.

## Fixed

- **A fresh container now starts.** The image's first start never created a database, so `nextsqld` exited with `this deployment has no database yet`. The production profile failed before that, and the HA seed backup had nothing to copy. First start now creates a database named by `NEXTSQL_DATABASE`, or `default` if unset.
- **`restore` and `verify` work under any UID in the image.** `/tmp` was writable only by uid 10001, so they failed with a permission error under any other non-root UID. `/tmp` is now writable by every UID, with the sticky bit set.

## Behavior changes

- `NEXTSQL_DATABASE` sets the database name on first start only. Later starts ignore it, so existing deployments are unaffected.
- Clients that send a database name must use the one the deployment was created with. Any other name fails with `authentication failed`. Clients that send no name are unaffected.

## Upgrade and compatibility

Stop the daemon, install the 0.0.9 Linux packages or pull the new image, and restart it. Confirm both the CLI and daemon report `0.0.9`.
There are no storage, WAL, catalog, or network protocol format breaks relative to 0.0.8.

Container users pin `docker.io/bzynchub/nextsql:0.0.9`. Image tags and release assets are immutable.

A volume left by a failed first start on an earlier image starts on this one, as long as settings written to `nextsql.conf` are unchanged. If they changed, the start fails with `config file ... already exists`. Put them back for the first start, or start from empty volumes.

If you are upgrading from a release before 0.0.8, read the [0.0.8 release notes](0.0.8.md) first. That release fixed a rollback bug that could damage data, and upgrading does not repair existing damage. Run `nextsql check-pages` on a restored copy of a recent backup.

## Known issues

- The HA compose cluster took 84 s and 157 s to start serving in two runs on a loaded host. The cause has not been investigated.
- On an HA cluster, followers answer `SHOW CLUSTER` with `not the leader`, although `docs/docker.md` says it works from any node.
- If `nextsql.db` is lost while the rest of the deployment remains, the container refuses to start, as it should, but reports `database is already initialized`.
